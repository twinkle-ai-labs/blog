# 그림부터 그리고 시작하자

만들려는 흐름은 단순하다.

```txt
master 브랜치에 push
        ↓
GitHub Actions가 Pelican 빌드
        ↓
결과물(output/)을 gh-pages 브랜치에 커밋
        ↓
GitHub Pages가 gh-pages를 서빙
```

원본(마크다운)과 결과물(HTML)이 서로 다른 브랜치에 산다는 게 핵심이다.
내가 손대는 건 `master` 하나뿐이고, `gh-pages`는 기계가 관리한다.

# 저장소 준비 — 토큰은 필요 없다

블로그를 올릴 저장소를 하나 만든다. `username.github.io`가 아니어도 되고,
그 경우 주소는 `https://username.github.io/저장소이름/`이 된다.

옛날 글들을 보면 여기서 PAT(Personal Access Token)를 발급받아 Secrets에 넣으라고 한다.
지금은 그럴 필요가 없다.

> **💡 `GITHUB_TOKEN`**
>
> 워크플로가 실행될 때마다 GitHub이 임시 토큰을 알아서 발급해준다.
> 워크플로에 `permissions: contents: write`만 주면 `gh-pages`에 푸시할 권한이 생긴다.
> 만료도 관리도 필요 없고, 그 실행이 끝나면 토큰도 함께 사라진다.

# 워크플로 한 장

빌드에 필요한 의존성을 `requirements.txt`에 적는다.

```txt
pelican==4.12.0
Markdown
typogrify
```

버전을 고정해 두는 걸 권한다. 내 노트북에서 되던 빌드가 몇 달 뒤 Actions에서만 깨지면,
원인을 찾는 데 걸리는 시간이 고정에 드는 수고보다 훨씬 크다.

그다음 `.github/workflows/pelican.yml`을 만든다.
Marketplace의 [GitHub Pages Pelican Build Action](https://github.com/marketplace/actions/github-pages-pelican-build-action)을 그대로 썼다.

```yaml
name: Pelican CI/CD

on:
  push:
    branches:
      - master

jobs:
  build:
    runs-on: ubuntu-latest

    # 내장 GITHUB_TOKEN에 push 권한을 준다
    permissions:
      contents: write

    steps:
      - uses: actions/checkout@v7
      - uses: nelsonjchen/gh-pages-pelican-action@0.2.0
        env:
          PELICAN_CONFIG_FILE: publishconf.py
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

`PELICAN_CONFIG_FILE`을 `publishconf.py`로 지정한 게 중요하다.
개발용 설정으로 빌드하면 주소가 전부 상대 경로로 나가서, 배포된 사이트의 링크가 어긋난다.

# 배포용 설정 손보기

`publishconf.py`는 `pelicanconf.py`를 상속한 뒤 배포에만 필요한 값을 덮어쓴다.

```python
from pelicanconf import *

SITEURL = "https://blog.twinklelabs.kr"
RELATIVE_URLS = False

DELETE_OUTPUT_DIRECTORY = True
```

`pelicanconf.py`에는 시간대와 기본 언어를 잡아둔다.

```python
TIMEZONE = 'Asia/Seoul'
DEFAULT_LANG = 'ko'
```

> **⚠️ CSS가 통째로 사라졌다면**
>
> 배포하고 나서 사이트가 스타일 없는 맨 HTML로 보인 적이 있다.
> 원인은 `SITEURL`이었다. 테마의 CSS·JS·이미지 경로는 전부 `SITEURL`을 기준으로 만들어지는데,
> 이 값이 비어 있거나 실제 주소와 다르면 브라우저가 없는 곳을 찾는다.
>
> * 끝에 슬래시(`/`)를 붙이지 않는다 — Pelican이 `{{ SITEURL }}/...` 형태로 이어 붙인다.
> * `http`가 아니라 **`https`**로 적는다.
> * 하위 경로에 배포한다면 그 경로까지 포함한다. (`https://user.github.io/blog`)

# 올리고, 켜기

프로젝트를 저장소에 올린다.

```shell
git init
git add .
git commit -m "first commit"
git branch -M master
git remote add origin [저장소 주소]
git push -u origin master
```

푸시하는 순간 Actions가 돌기 시작한다. Actions 탭에서 초록 체크가 뜨면
`gh-pages` 브랜치가 새로 생겨 있을 것이다.

마지막으로 `Settings → Pages`에서 **Source를 `gh-pages` 브랜치 / `root`** 로 맞춰준다.
1~2분 뒤 주소로 들어가면 블로그가 열린다. 🎉

## 커스텀 도메인 붙이기

내 도메인을 쓰려면 두 가지가 필요하다.

**① DNS** — 도메인 관리 페이지에서 GitHub Pages를 가리키게 한다.
서브도메인이면 `CNAME` 레코드로 `username.github.io`를 가리키면 된다.

**② `CNAME` 파일** — 저장소가 아니라 **배포되는 결과물**에 들어가야 한다.
이걸 몰라서 `gh-pages`가 갱신될 때마다 도메인 설정이 풀리는 걸 한참 봤다.

이 액션은 환경 변수 하나로 처리해준다.

```yaml
      - uses: nelsonjchen/gh-pages-pelican-action@0.2.0
        env:
          GH_PAGES_CNAME: blog.twinklelabs.kr
          PELICAN_CONFIG_FILE: publishconf.py
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Pelican 쪽에서 직접 넣고 싶다면, `content/extra/CNAME`에 도메인을 적고
정적 파일로 복사되게 설정해도 된다.

```python
STATIC_PATHS = ["images", "extra/CNAME"]
EXTRA_PATH_METADATA = {
    "extra/CNAME": {"path": "CNAME"},
}
```

# 마치며

이제 글을 쓰고 `git push` 하면 몇 분 뒤 블로그가 알아서 갱신된다.
배포를 잊어버릴 수 있게 되었다는 게 이 작업의 진짜 결과물이다.

남은 건 생김새다. 기본 테마도 나쁘지 않지만, 내 블로그가 남의 옷을 입고 있는 기분은 어쩔 수 없다.
테마를 직접 만들려면 Pelican이 쓰는 템플릿 엔진부터 알아야 한다.
