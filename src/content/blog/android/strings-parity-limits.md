스페인어 리소스 `values-es/strings.xml`을 열어보니 일부 버튼이 영어로 남아 있었습니다. 프랑스어 파일에는 스페인어도 섞여 있었습니다. 번역 키를 확인하는 CI 검사는 계속 통과하던 상태였습니다.

지원 언어는 한국어, 영어, 일본어, 중국어 간체·번체, 스페인어, 독일어, 프랑스어, 이탈리아어, 포르투갈어, 인도네시아어로 11개였습니다. 언어별로 새 문자열의 키가 빠지는 것을 막으려고 `strings-parity.sh`를 사용했습니다.

```bash
# strings-parity.sh의 핵심 로직
# 기본 언어(ko/en)의 모든 <string name="..."> 키가 다른 10개 언어 파일에도 존재하는지 검사
```

이 검사가 Exit 0으로 끝나면 11개 언어의 240개 키가 맞는다고 판단했습니다. 그러나 키가 있다는 사실을 번역이 끝났다는 뜻으로 받아들이고 있었습니다.

## 키는 있었지만 값이 번역되지 않았습니다

스페인어 파일에는 다음처럼 번역된 문장과 영어 문장이 함께 있었습니다.

```xml
<!-- values-es/strings.xml -->
<string name="action_scan_document">Scan Document</string>
<string name="msg_delete_confirm">¿Estás seguro de que deseas eliminar?</string>
<string name="btn_upgrade_pro">Upgrade to PRO</string>
```

`action_scan_document`와 `btn_upgrade_pro`는 존재하므로 키 검사를 통과합니다. 하지만 스페인어 화면을 사용하는 사람에게는 영어 버튼이 표시됩니다.

기능을 추가할 때 기본 언어의 값을 복사해 두었던 것이 배포본까지 남았습니다. `strings-parity.sh`가 확인한 것은 키의 누락이며, 각 값이 해당 언어로 작성됐는지는 검사하지 않았습니다.

## 같은 문자열을 모두 오류로 처리할 수는 없었습니다

영어와 값이 100% 같으면 실패시키는 방식도 생각할 수 있습니다. 하지만 서로 다른 언어에서 같은 철자를 쓰는 경우가 있습니다.

- `Cancelar`는 스페인어와 포르투갈어에서 모두 취소 버튼에 사용합니다.
- `Information`은 영어와 프랑스어의 철자가 같습니다.
- `PDF`, `PRO`, `OK`는 언어가 달라져도 유지하는 공통 표기입니다.

따라서 값이 같다는 이유만으로 자동 교체하거나 오류로 확정하면 정상 번역까지 수정할 수 있습니다. 동일한 값은 검토할 후보로 사용하되, 문맥을 확인한 뒤 처리해야 했습니다.

## 후보 추출과 번역 판단을 나눴습니다

11개 언어를 정리하면서 세 가지 기준을 적용했습니다.

첫째, 스크립트로 동일 문자열 후보를 모으고 언어별 문맥과 대조해 수정할 항목을 정했습니다. 기계가 후보를 찾는 일과 번역이 맞는지 읽는 일을 구분했습니다.

둘째, 같은 단어를 쓰더라도 각 언어 파일에 값을 독립적으로 뒀습니다. 포르투갈어와 스페인어의 `Cancelar`를 참조로 묶지 않아, 나중에 한 언어의 표현을 바꿀 때 다른 언어까지 따라 바뀌지 않도록 했습니다.

셋째, 미번역 임시 값에는 `TODO_TRANSLATE_` 같은 표시를 붙였습니다. CI에서 키가 있는지뿐 아니라 임시 값이 남아 있는지도 확인하도록 보완했습니다.

이후에도 키 검사만으로 번역의 정확성을 판단하지 않기로 했습니다. 키 누락과 임시 값은 자동 검사로 찾고, 실제 화면에 표시할 문구는 해당 언어의 문맥에서 확인합니다.
