물타기 계산기에서 같은 날 버그 둘이 나왔다.

**하나.** 단가에 `0`을 넣으면 오류도 결과도 안 나왔다. 화면이 아무 말도 안 했다.

**둘.** 목표 평단가 칸은 아무도 검증하지 않았다. `0`을 친 사람에게 엉뚱한 이유를 댔다.

각각 고치는 건 어렵지 않았다. 그런데 둘을 나란히 놓으니 같은 병이었다.

---

# 하나 — 같은 규칙이 두 곳에 다르게 적혀 있었다

```kotlin
// 검증하는 쪽
fun validatePrice(price: Double?): Error? =
    if (price != null && price < 0) Error.Negative else null

// 계산하는 쪽
val isValid = price != null && price > 0
```

`< 0`과 `> 0`. **`0`이 두 판정 사이의 틈으로 빠졌다.**

검증하는 쪽은 «0은 음수가 아니니 통과»라고 했고,
계산하는 쪽은 «0은 양수가 아니니 계산 안 함»이라고 했다.
그래서 오류도 없고 결과도 없었다.

---

# 둘 — 검사 함수의 네 번째 자리

입력 칸이 넷이었고 검사 함수가 넷을 받았다. 그런데 마지막 자리의 이름이 `BUY_QUANTITY`였다.

목표 평단가 모드에는 «살 수량» 칸이 없다. 그래서 그 모드는 네 번째 자리에 `null`을 넘겼고,
**그 자리에 실제로 서 있던 «목표 평단가» 칸이 통째로 검증을 빠져나갔다.**

이름이 착각을 만들었다. `BUY_QUANTITY`라는 자리 이름이
«목표 모드에는 검사할 칸이 없다»는 생각의 뿌리였다.
자리는 자리 이름(`FOURTH`)으로, 뜻은 따로(`InputKind`)로 뒀어야 했다.

---

# 고친 뒤에도 구조는 그대로였다

값을 맞추고 `null`을 없앴다. 두 버그는 사라졌다. 그런데 구조가 안 바뀌었다.

계산 함수는 여전히 이렇게 생겼다.

```kotlin
fun calculate(price: Double?, quantity: Double?, /* … */): Result? {
    val isValid = price != null && price > 0 && /* … */   // ← 또 센다
    if (!isValid) return null
    // …
}
```

`Double?`을 받는 함수는 **누가 부르든 제 몸을 지키려고 다시 센다.**
그게 두 번째 사본이다. 사본이 있는 한 셋째 버그는 시간 문제였다.

---

# 왜 두 번째 사본이 생기는가

«한 규칙이 두 곳에 적히면 갈린다»는 건 다들 안다.
알면서도 두 곳에 적게 되는 이유가 있다.

**호출하는 쪽이 검증됐는지를 알 길이 없어서다.**

`calculate(price: Double?)`라는 서명은 «검증된 값을 주세요»라고 말할 방법이 없다.
`Double?`은 그냥 숫자거나 없음이다. 그러니 받는 쪽은 방어한다. 방어가 사본이다.

---

# 타입이 «이미 검증됐다»를 들고 온다

그래서 걷었다.

```kotlin
sealed interface Validation {
    data class Valid(val inputs: ValidInputs) : Validation
    data object Incomplete : Validation
    data class Invalid(val kind: InputKind, val reason: Reason) : Validation
}

fun validateInputs(raw: RawInputs): Validation

// 계산 함수는 ValidInputs 만 받는다
fun calculate(inputs: ValidInputs): Result
```

바뀐 것은 세 가지다.

**판정이 한 곳에서만 난다.** `validateInputs` 하나가 셋 중 하나를 낸다.
결과를 만드는 쪽과 오류 문구를 만드는 쪽이 **같은 판정에서 갈라진다.**
전에는 각자 세다가 서로 다른 답을 냈다.

**계산 함수가 다시 셀 이유가 없다.** `ValidInputs`를 들고 있다는 건
이미 통과했다는 증명이다. 방어할 것이 없으니 사본도 없다.

**검증 안 된 값은 컴파일이 안 된다.** 이게 제일 크다.
«검증을 깜빡한 경로»가 생길 수 없다 — 그런 코드는 빌드가 안 되니까.
둘째 버그(아무도 검증하지 않는 칸)는 이 구조에서 **적히는 것 자체가 불가능**하다.

---

# `null`이 하나의 뜻만 갖게 됐다

덤이 하나 있었다. 전에는 `null`이 두 가지를 뜻했다.

- **틀린 입력** — 사용자가 잘못 쳤다
- **닿을 수 없다** — 아직 다 안 쳤다

받는 쪽은 둘을 구분할 수 없으니 **추측했다.** 그리고 그 추측이 화면의 문장이 됐다.
`0`을 친 사람에게 엉뚱한 이유를 댄 게 이것이다.

`Incomplete`와 `Invalid`가 갈리자 추측할 일이 없어졌다.

---

# 예외 하나 — 검증 앞에서 불리는 힌트

치는 중에 «≈ n주»라는 힌트를 보여 준다. 이건 검증 **전에** 불린다.
`0`을 받아도 무언가 보여 줘야 하고, 그래서 `ValidInputs`를 요구할 수 없다.

그 자리의 검사는 남기고, KDoc에 사정을 적었다.
예외를 두는 건 괜찮은데 **왜 예외인지 적히지 않은 예외**가 다음 사본의 씨앗이 된다.

# 정리

- 규칙이 두 곳에 적힌 것을 보면 값을 맞추는 데서 멈추지 않는다.
  **왜 두 번째 사본이 필요했는가**를 묻는다. 대개 답은 «호출하는 쪽이 모르기 때문»이고,
  그 답의 답은 검증된 값의 타입이다.
- `null`·`Optional`에 뜻을 둘 담지 않는다. 둘이면 받는 쪽이 추측하고,
  추측은 화면에서 말이 된다.
- 자리 이름과 뜻을 섞지 않는다. `BUY_QUANTITY`가 네 번째 자리의 이름이 되는 순간,
  그 자리에 다른 것이 설 때 아무도 못 알아본다.
