물타기 계산기(Stock Calculator)를 Play 스토어 테스트 트랙에 올린 뒤 Pocket PDF 개발을 시작했습니다. 카메라로 찍거나 불러온 문서 이미지를 PDF로 묶고, 이미지 안의 글자를 검색하고 복사할 수 있게 하는 앱입니다.

첫 편은 검색 가능한 PDF를 만드는 과정에서 한글이 사라진 문제를 다룹니다. 화면에서는 OCR이 끝났다고 표시했지만, 생성된 PDF에서는 한글을 찾을 수 없었습니다.

## 이미지 위에 투명한 글자층을 넣었습니다

이미지만 들어 있는 PDF에서는 사진 속 글자를 텍스트로 검색할 수 없습니다. OCR로 인식한 문자열을 이미지와 같은 위치에 넣어 검색과 복사가 가능하도록 했습니다.

먼저 ML Kit OCR에서 텍스트 블록, 줄, 단어의 문자열과 바운딩 박스 좌표를 받았습니다. 이미지의 픽셀 좌표는 PDF 페이지의 포인트(Point, 72 DPI) 좌표로 변환했습니다.

`InvisibleTextLayer`는 스캔 이미지를 배경에 그리고, 인식한 글자를 투명 렌더링 모드인 `RenderingMode.NEITHER_FILL_NOR_STROKE`로 그 위에 배치합니다. 화면에는 사진이 보이지만 PDF 안에는 검색할 문자열도 들어가는 구조입니다.

## 좌표 계산을 합치다가 문자 필터를 발견했습니다

처음에는 이미지→PDF 변환기와 실시간 문서 스캐너가 좌표 계산 함수를 각각 가지고 있었습니다. 두 구현을 `InvisibleTextLayer`로 모으면서 문자 정제 함수도 다시 읽었습니다.

```kotlin
// InvisibleTextLayer 내부의 문자 정제 함수
private fun sanitize(text: String): String {
    // 과거 누군가 넣어둔 영문 전용 필터
    return text.map { char ->
        if (char.code < 256) char else ' '
    }.joinToString("")
}
```

이 함수는 코드값이 256 이상인 문자를 모두 공백으로 바꾸고 있었습니다. 한글 음절은 `U+AC00`부터 시작하므로 필터를 통과할 수 없었습니다. OCR에서 문자열을 인식해도 PDF에 넣기 전에 지워지는 구조였습니다.

한글이 없어지는 원인은 좌표가 아니라 이 필터였습니다. 중복 구현을 합치는 과정에서 발견했고, 한글을 보존하도록 고쳤습니다.

## 폰트와 ToUnicode 매핑도 확인했습니다

문자열을 남긴 뒤에는 PDF 뷰어가 그 글자를 유니코드로 읽을 수 있어야 했습니다. 안드로이드 연재 11편에서 다룬 `/ToUnicode` CMap도 이 과정에 필요했습니다.

Pretendard(OFL)에서 현대 한글 2,350자와 필수 기호를 추출하는 `tools/bake-ocr-font.py`를 만들었습니다. 생성한 OTF 서브셋은 380KB였고, 앱에 포함해 사용했습니다.

JVM 단위 테스트에서는 `pdfbox-android`로 만든 PDF의 ToUnicode를 역추출했습니다. OCR 좌표와 폰트 포함 여부만 확인하는 데서 끝내지 않고, 넣은 한글을 다시 텍스트로 읽을 수 있는지 검사했습니다. 이 테스트로 확인한 범위 안에서 한글 검색에 필요한 매핑이 유지되는 것을 검증했습니다.

이 작업 이후 이미지 변환기와 실시간 스캐너는 같은 글자층 구현을 사용하게 됐습니다. 3편에서는 앱과 웹의 딥링크 경로를 맞춘 과정을 다룹니다.
