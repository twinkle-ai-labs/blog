물타기 계산기에 광고를 붙이는 데 하루를 썼습니다. SDK 코드뿐 아니라 AdMob 콘솔에서 앱과 광고 단위를 만들고, 동의와 구매 상태에 따라 요청을 제어해야 했습니다.

이 글은 2026년 8월 테스트 트랙을 준비하면서 적용한 구성과 당시 확인한 정책을 기록한 것입니다.

## 앱 ID와 광고 단위 ID를 구분했습니다

AdMob에서 받은 ID는 용도가 둘로 나뉘었습니다.

- 앱 ID (`ca-app-pub-…~…`): 앱마다 하나이며 매니페스트에 넣습니다.
- 광고 단위 ID (`ca-app-pub-…/…`): 광고 자리마다 만들고 코드에서 사용합니다.

물결(`~`)과 빗금(`/`)으로도 구분할 수 있습니다.

```xml
<meta-data
    android:name="com.google.android.gms.ads.APPLICATION_ID"
    android:value="ca-app-pub-…~…" />
```

앱 ID를 빠뜨리거나 잘못 넣었을 때는 광고가 보이지 않는 정도로 끝나지 않았습니다. SDK가 예외를 발생시켜 앱이 시작하자마자 종료됐습니다. 처음에는 광고 설정과 앱 실행 실패를 연결하지 못했습니다.

## 세 가지 광고를 배치했습니다

배너는 바텀바 위에 두었습니다. 전면 광고는 계산을 저장한 뒤 세 번에 한 번, 보상형 광고는 무료 종목 3개를 넘겨 만들 때 사용했습니다.

각 자리는 AdMob 콘솔에서 광고 단위를 따로 만들었습니다. 이 과정에서 보상형과 보상형 전면(베타)을 혼동했습니다. 둘은 다른 형식이며, 콘솔에서 만든 형식과 코드에서 사용하는 클래스가 맞아야 합니다. 잘못 조합했을 때 SDK가 로드를 거절했지만, 에러 메시지만으로 원인을 바로 찾지는 못했습니다.

## 테스트 광고는 빌드 종류로 나눴습니다

테스트 ID로 출시하면 실제 광고 수익이 발생하지 않습니다. 반대로 개발 중 실제 광고를 반복해서 누르면 계정 정지 위험이 있습니다. 매번 ID를 바꾸는 대신 빌드에서 선택하게 했습니다.

```kotlin
object AdUnits {
    private const val TEST_BANNER = "ca-app-pub-3940256099942544/9214589741"

    val BANNER = if (BuildConfig.DEBUG) TEST_BANNER
                 else "ca-app-pub-…/…"   // 실제 단위
}
```

디버그 빌드에는 구글 공식 테스트 단위를, 릴리스에는 실제 단위를 사용했습니다. 매니페스트의 앱 ID는 양쪽 모두 실제 ID를 썼습니다. 당시 확인한 안내에 맞춰 실제 앱 ID와 테스트 광고 단위를 조합했습니다.

## UMP의 동의 상태를 함께 확인했습니다

당시 EEA·영국·스위스 사용자를 대상으로 광고를 제공하려면 인증된 동의 플랫폼(CMP)을 사용해야 했습니다. 필요한 동의 절차가 끝나기 전에 광고를 요청하지 않도록 구글의 무료 UMP(User Messaging Platform) SDK를 붙였습니다.

모든 사용자에게 같은 폼을 띄우는 방식은 아니었습니다. UMP가 동의가 필요한지 판단하도록 했고, 한국 사용자에게 동의가 불필요하다고 응답하면 폼 없이 광고 요청을 허용했습니다.

```kotlin
object ConsentGate {
    var canRequestAds by mutableStateOf(false)
        private set
    …
}
```

배너, 전면, 보상형 광고는 요청 전에 모두 `canRequestAds`를 확인합니다. 각 광고가 동의 상태를 따로 판단하지 않게 했습니다.

동의를 다시 선택할 수 있어야 하는 지역에는 설정의 ‘광고 개인정보 선택’ 항목을 표시했습니다. 이 항목이 필요하지 않은 경우에는 숨겼습니다.

## 광고가 화면 조작을 방해하지 않게 했습니다

### 배너 높이는 미리 확보했습니다

광고를 받은 뒤에야 자리를 만들면 화면이 밀립니다. 사용자가 누르려던 버튼 위치가 광고로 바뀌지 않도록, 로드 전에도 배너 높이를 비워뒀습니다.

키패드가 올라올 때는 배너를 숨겼습니다. 숫자를 입력하는 영역 가까이에 광고를 두어 잘못 누르게 하는 상황을 피하려는 선택이었습니다.

### 전면 광고는 저장이 끝난 뒤에만 표시했습니다

계산 중에는 전면 광고를 띄우지 않았습니다. 저장을 마쳤고 광고도 미리 로드된 경우에만 표시했습니다. 광고가 준비되지 않았다면 다음 요청을 준비하고 저장 흐름은 그대로 끝냈습니다.

```kotlin
fun onSaved(activity: Activity) {
    saves += 1
    if (saves % everyN != 0) { preload(activity); return }
    val ad = loaded ?: run { preload(activity); return }   // 준비 안 됐으면 그냥 보냅니다
    …
}
```

이렇게 해야 광고 로드 시간 때문에 저장 완료가 늦어지지 않습니다.

### 배너 객체를 재사용했습니다

처음에는 컴포저블 안에서 `AdView`를 만들었습니다. 키패드를 여닫을 때마다 객체가 파괴되고 다시 생성되면서 광고를 새로 요청했습니다. 그 과정에서 배너가 비어 있는 현상을 봤습니다.

당시에는 잦은 요청이 광고 채움과 무효 트래픽 판단에 영향을 줄 수 있다고 보고, 배너를 한 번 만들어 앱이 실행되는 동안 재사용하도록 바꿨습니다.

## 광고 제거 구매를 복원했습니다

Play Billing에는 광고 제거용 비소모성 상품 하나를 등록했습니다. 한 번 구매하면 광고를 제거하고, 앱을 다시 설치해도 같은 구글 계정의 구매 상태를 확인하도록 했습니다. 앱 시작 시 자동으로 확인하므로 별도의 복원 버튼은 두지 않았습니다.

당시 구매 처리에서 주의한 조건은 확인(acknowledge) 기한이었습니다. 구매를 확인하지 않으면 구글이 3일 뒤 자동 환불하므로, 소유 상태를 조회할 때 미확인 구매도 함께 처리했습니다.

구매가 확인된 사용자에게는 광고 제거 항목을 숨겼습니다. 이미 구매한 상품을 다시 살 수 있는 것처럼 보이지 않게 하려는 목적입니다.

## 에뮬레이터에서는 DNS 때문에 광고가 비었습니다

배너 공간은 생겼는데 광고가 채워지지 않는 문제도 있었습니다. 당시 기본 설정으로 실행한 에뮬레이터가 `googleads.g.doubleclick.net`을 해석하지 못했습니다.

    Unable to resolve host … No address associated with hostname
    Ad failed to load : 0

이 문제를 찾는 데 반나절이 걸렸습니다. DNS를 지정해 실행한 뒤에는 테스트 광고가 정상으로 표시됐습니다.

```
emulator -avd <이름> -dns-server 8.8.8.8,1.1.1.1
```
