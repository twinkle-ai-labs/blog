광고와 결제를 붙인 뒤 Play 업로드를 준비하는 데 이틀이 더 걸렸습니다. 서명 키와 버전 번호를 정하고, 등록정보와 서비스 계정 권한을 설정하는 과정이었습니다.

이 글은 2026년 8월 22일의 기록입니다. 당시 앱은 테스트 트랙에 있었고, 프로덕션으로 승격하기 전이었습니다. 정책과 콘솔 조건도 그때 준비한 기준으로 적었습니다.

## 앱 서명과 업로드 키를 나눴습니다

Play 앱 서명을 사용해 최종 앱 서명 키는 구글에 맡겼습니다. 제가 관리할 키는 업로드 권한을 확인하는 업로드 키였습니다.

직접 최종 서명 키를 관리하는 방식에서는 키를 잃으면 같은 앱을 업데이트할 수 없고 새 패키지명으로 배포해야 합니다. 업로드 키는 잃더라도 콘솔에서 재설정을 요청할 수 있습니다. 당시에는 재설정에 며칠이 걸리는 것으로 확인했습니다. 키를 잃었을 때 요청부터 다시 시작하지 않으려면 별도 백업도 필요했습니다.

```kotlin
val keystoreProperties = rootProject.file("keystore.properties")
if (keystoreProperties.exists()) {
    val props = Properties().apply { keystoreProperties.inputStream().use { load(it) } }
    signingConfigs {
        create("release") {
            storeFile = rootProject.file(props.getProperty("storeFile"))
            storePassword = props.getProperty("storePassword")
            …
        }
    }
}
```

키와 비밀번호는 git에 넣지 않았습니다. `keystore.properties`가 없는 기계나 CI에서는 서명 없이 빌드되도록 했습니다. 서명 정보를 저장소에 포함하는 대신, 필요한 환경에만 별도로 제공하는 구성을 택했습니다.

## 두 버전 번호의 역할이 달랐습니다

| | 무엇 | 되돌릴 수 있나 |
|---|---|---|
| `versionCode` | 콘솔이 세는 정수 | 아니오. 한 번 사용한 번호를 다시 받지 않습니다 |
| `versionName` | 사용자에게 보이는 버전 문자열 | 가능합니다. `versionCode`와 같은 증가 규칙을 따르지 않습니다 |

시험 삼아 번들을 올릴 때 `versionCode = 1`을 사용했습니다. 그 번호를 다시 쓸 수 없어서 다음 업로드는 2부터 시작했습니다.

```kotlin
// versionCode 1은 예전 번들이 Play 콘솔에 먹었습니다 — 콘솔은 한 번 본 코드를 다시 받지 않아요
versionCode = 6
versionName = "1.0.0"
```

테스트 트랙에 세 번 올리는 동안 `versionName`은 1.0에서 1.3까지 바뀌었습니다. 아직 공개판을 내지 않은 상태였으므로 1.3.0을 첫 공개판 번호로 쓰는 대신 표시 버전을 1.0.0으로 되돌렸습니다. `versionCode`는 계속 증가시켰습니다.

## 당시 일정에 맞춰 targetSdk를 올렸습니다

신규 앱과 업데이트에는 Play의 타겟 API 요구사항이 적용됩니다. 당시 작업에서는 2026-08-31을 마감으로, API 36을 요구 수준으로 잡고 준비했습니다.

    Chore: targetSdk 를 36 으로 올린다 — Play 마감 2026-08-31

`targetSdk`를 올리면 권한이나 백그라운드 제한 같은 동작이 바뀔 수 있습니다. 번호를 바꾸는 것에 더해 앱 동작을 다시 확인해야 하는 작업이므로, 출시 직전에 처리하기에는 부담이 있었습니다.

## 정책 문서와 고지를 준비했습니다

콘솔에 제출할 개인정보 처리방침을 웹에 게시했습니다. 계산 기록을 서버로 보내지 않는 구조와 별개로, 광고 SDK의 데이터 처리는 확인해야 했습니다. 데이터 보안 양식에도 무엇을 수집하고 어디로 보내는지 선언했습니다.

앱 콘텐츠 설문에서는 광고 포함 여부, 타겟 연령층, 콘텐츠 등급을 작성했습니다. 앱 설정에는 다음 고지도 넣었습니다.

- 오픈소스 라이선스: 사용하는 Pretendard 글꼴의 SIL OFL 1.1 고지
- 투자 면책: 금융 계산 도구이며 투자 자문을 제공하지 않는다는 설명

당시에는 두 항목을 배포에 필요한 고지로 관리했고, 설정 화면에서 빠지지 않도록 테스트에 포함했습니다.

## 11개 언어의 등록정보를 만들었습니다

제목, 짧은 설명, 긴 설명, 스크린샷과 함께 512×512 아이콘, 1024×500 피처 그래픽을 준비했습니다. 스크린샷은 11개 언어에 5장씩, 모두 55장이었습니다.

스크린샷은 에뮬레이터에서 자동으로 찍었습니다. 좌표를 고정하면 언어별 글자 길이에 따라 버튼이 밀릴 수 있어서, `uiautomator`로 요소를 찾아 누르게 했습니다. 독일어 화면에서도 같은 기능을 캡처하기 위한 방식입니다.

## Gradle에서 업로드하도록 설정했습니다

Gradle Play Publisher 플러그인으로 번들과 등록정보를 올리게 했습니다.

```
./gradlew publishReleaseBundle                       # 내부 테스트
./gradlew publishReleaseBundle --track production     # 프로덕션
./gradlew publishReleaseListing                       # 등록정보·스크린샷
```

Google Cloud에서 서비스 계정 키를 만들고 Play 콘솔에서 권한을 부여했습니다. 이 과정에서 두 오류를 만났습니다.

`accessNotConfigured`는 Cloud 프로젝트에서 Google Play Android Developer API를 켜지 않아 발생했습니다. 당시 이 API는 무료였고 켜는 데는 1분 정도였지만, 원인을 찾는 데 30분이 걸렸습니다.

`The caller does not have permission`은 Play 콘솔의 ‘사용자 및 권한’에서 서비스 계정에 앱 접근과 출시 권한을 주어 해결했습니다. Cloud IAM 역할을 바꾸는 것으로는 해결되지 않았습니다.

처음에는 두 오류를 키 문제로 보고 키를 여러 번 다시 만들었습니다. 실제로 확인할 곳은 API 활성화와 Play 콘솔 권한이었습니다.

## 스크린샷 55장이 업로드 대상에서 빠졌습니다

글을 쓰다가 등록정보 폴더가 잘못된 것을 발견했습니다. 11개 로케일의 파일을 `app/play/`에 만들었지만, 플러그인이 읽는 경로는 `app/src/main/play/`였습니다.

빌드와 업로드가 모두 성공해서 누락을 알아채지 못했습니다. 실제로 올라간 것은 스크린샷 3장과 옛 문구가 담긴 기존 한국어 등록정보뿐이었습니다.

업로드 전에 플러그인이 모은 파일을 확인할 수 있는 명령도 있습니다.

```
./gradlew generateReleasePlayResources
# → app/build/generated/gpp/release/play/ 아래에 실제로 올라갈 것이 모입니다
```

명령 실행 뒤 생성된 디렉터리를 보면 등록정보와 스크린샷이 업로드 대상에 포함됐는지 확인할 수 있습니다.

## 기본 업로드 대상은 내부 테스트로 뒀습니다

당시 사용한 트랙은 다음과 같았습니다.

- 내부 테스트: 최대 100명, 심사 대기가 거의 없어 개발 중 사용
- 비공개 테스트: 지정한 테스터 대상
- 공개 테스트: 누구나 참여 가능
- 프로덕션: 전체 공개

```kotlin
play {
    track.set("internal")
    defaultToAppBundles.set(true)
    releaseStatus.set(ReleaseStatus.COMPLETED)
}
```

기본값은 내부 테스트입니다. 프로덕션으로 올릴 때만 `--track production`을 명시하도록 했습니다.

앱을 만드는 데 열흘, 업로드 준비에 이틀을 썼습니다. 이 네 편에는 그 과정에서 확인한 키, 번호, 권한, 파일 경로를 남겼습니다. 작성 시점에는 여전히 테스트 트랙에 있었으며, 앱 내부에서 배운 내용은 [안드로이드를 만들며 배운 것](/category/android/) 시리즈에 따로 기록하고 있습니다.
