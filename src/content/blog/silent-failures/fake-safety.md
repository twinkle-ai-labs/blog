Pocket PDF에 인앱 결제와 구독 비즈니스 모델(BM)을 추가하던 날, 기존 검증과 문서에서 세 가지 문제를 찾았습니다. 프로모션 코드는 평문으로 통과할 수 있었고, 광고 ID 검사는 새 유형을 일부 놓쳤으며, CHANGELOG에는 아직 출시하지 않은 기능이 들어 있었습니다.

검사나 문서가 존재한다는 사실보다 실제로 어떤 조건과 버전을 확인하는지 살펴봐야 했습니다.

## 해시 비교 앞의 평문 조건으로 PRO가 열렸습니다

PRO 프로모션 코드는 입력을 SHA-256 해시로 바꿔 저장된 값과 비교하도록 돼 있었습니다. 그러나 그 앞에 테스트용 평문 비교가 `||`로 연결돼 있었습니다. 문제를 보여주는 코드입니다.

```kotlin
// 겉보기에는 안전한 SHA-256 검증 구조
fun isProCode(input: String): Boolean {
    val inputHash = sha256(input.trim())
    return input.equals("pro", ignoreCase = true)
        || input.equals("premium", ignoreCase = true)
        || inputHash == PROMO_SECRET_HASH
}
```

`pro`나 `premium`을 입력하면 해시가 일치하지 않아도 참이 됩니다. 실제 코드에는 평문 조건이 넷 있었고, `pro` 한 단어로 월 ₩1,900, 연 ₩14,900, 평생 ₩19,900의 PRO 기능이 열렸습니다.

`PROMO_SECRET_HASH`에 저장된 옛 해시도 확인했습니다. 후보를 해시해 비교했지만 맞는 코드를 찾지 못했고, 어떤 입력을 위해 남겨둔 값인지 알 수 없었습니다.

평문 조건 넷과 알 수 없는 옛 해시를 제거하고, 검증에 사용할 해시 하나만 남겼습니다. 해시 비교가 있다는 설명만 읽으면 놓치기 쉬웠지만, 앞의 평문 분기는 그 비교를 거치지 않고도 통과하는 경로였습니다.

## 보상형은 견본 검사에만 포함돼 있었습니다

`admob-ids.sh`는 출시용 광고 ID에 Google 테스트 ID가 들어 있는지, 값이 비어 있는지를 검사했습니다. 이 중 빈 값 검사의 대상은 배너와 전면 광고뿐이었습니다.

```bash
# admob-ids.sh
CHECK_TARGETS="ADMOB_BANNER ADMOB_INTERSTITIAL"
```

이 목록에는 그날 추가된 보상형 광고가 없습니다. 보상형의 견본 ID는 검사에 걸렸지만, 그 값을 비우면 빈 값 검사에서는 놓치는 상태였습니다.

빈 값 검사 목록에 `ADMOB_REWARDED`를 추가했습니다. 광고 유형이 늘어날 때 두 검사의 대상도 함께 확인해야 했습니다.

## v1.0.0에 없던 기능이 출시 기록에 들어 있었습니다

CHANGELOG의 v1.0.0 절에는 해당 버전에 없던 고급 기능이 적혀 있었습니다. 커밋을 확인하니 그 기능의 소스는 출시 다음 날 밤에 처음 들어왔습니다. 이미 배포한 바이너리와 기록이 맞지 않았습니다.

v1.0.0 위에 `미출시 (Unreleased)` 절을 만들고 아직 내보내지 않은 변경을 분리했습니다. 다음 버전 번호는 이때 정하지 않았습니다. 출시 시점에 실제 변경을 보고 정해야 했습니다.

프로모션 코드에서는 통과 가능한 조건을, 광고 검사에서는 대상 목록을, CHANGELOG에서는 출시 커밋을 확인했습니다. 각각의 수정은 작았지만, 기존 장치가 무엇을 보장하는지 다시 읽어야 찾을 수 있는 차이였습니다.
