Gradle Play Publisher(GPP)로 구글 플레이 등록정보를 올렸는데, 며칠이 지나도 스토어 이미지가 바뀌지 않았습니다. 실행한 명령은 텍스트와 이미지를 함께 올리는 명령이었습니다.

```bash
./gradlew publishReleaseListing
```

어느 로케일에서 실패했는지와 실제로 무엇이 반영됐는지를 따로 확인해야 했습니다.

## 한 로케일의 실패가 편집 전체를 취소했습니다

플레이 API는 편집(edit)을 열고 변경을 넣은 뒤 커밋하는 방식으로 동작합니다. 커밋하기 전에는 변경이 반영되지 않으며, 같은 편집 안의 변경은 함께 반영되거나 함께 취소됩니다.

GPP 4.1.1은 등록정보 텍스트와 이미지를 같은 편집에서 올립니다. 이번에는 새 언어를 추가하면서 여러 로케일에 `graphics/` 폴더를 만들었고, 그중 일부는 스토어에 아직 존재하지 않았습니다.

GPP는 이미지를 올리기 전에 GET 요청으로 현재 이미지 목록을 읽습니다. 없는 로케일에서 이 요청이 404로 실패했습니다.

```
Listing for language 'fr-FR' not found
```

이 실패로 편집 전체가 취소됐습니다. 이미 존재하던 ko-KR의 이미지 변경도 반영되지 않았습니다. 빌드 로그 마지막에는 다음 한 줄이 남았습니다.

```
FAILED
```

로그는 작업이 실패했다는 사실을 보여줬지만, 어느 이미지까지 반영되지 않았는지는 알려주지 않았습니다.

## 콘솔에서 본 이미지와 API의 해시를 구분했습니다

편집의 원자성 덕분에 변경의 일부만 올라가는 일은 막을 수 있었습니다. 대신 한 로케일의 오류가 다른 로케일의 변경까지 취소할 수 있으므로, 실패한 항목만 다시 보면 반영 상태를 잘못 판단할 수 있었습니다.

콘솔 화면에서는 검토 중인 이미지와 반영된 이미지를 구분하기 어려웠습니다. 바뀐 이미지가 보이는 것만으로 업로드를 확인하지 않고 API로 이미지 목록을 읽었습니다.

임시 편집을 만들고, 이미지 목록이 반환하는 sha1을 로컬 파일의 해시와 비교한 뒤 그 편집을 삭제했습니다. 읽기만 했으므로 삭제해도 반영된 변경은 없습니다.

```bash
# 1. edit 을 만듭니다
# 2. GET listings/{lang}/phoneScreenshots → 각 이미지의 sha1
# 3. 로컬 파일의 shasum 과 맞춥니다
shasum fastlane/metadata/android/ko-KR/images/phoneScreenshots/*.png
# 4. edit 을 DELETE
```

API에서 읽은 이미지의 해시와 로컬 파일의 해시가 같으면 같은 파일인지 확인할 수 있습니다. 다르면 기대한 이미지가 그 목록에 없는 것입니다.

## 로케일을 먼저 만들고 이미지를 올렸습니다

스토어에 없는 로케일은 두 번에 나눠 처리했습니다.

1. 새 로케일의 `graphics/`를 잠시 치우고 등록정보를 올려 로케일을 만듭니다.
2. `graphics/`를 원래 자리로 되돌린 뒤 다시 실행해 이미지를 올립니다.

작업이 끝난 뒤 저장소의 파일 배치는 그대로였습니다. 업로드 순서만 나눴습니다.

REST 요청으로 로케일만 먼저 만드는 방법도 시도했습니다. 이때는 `edits:validate`가 200을 반환했지만 `edits:commit`은 HTML 404를 반환했습니다. 이 경로로는 완료하지 못했고, 커밋은 플러그인에 맡겼습니다.

## 실행 뒤에 반영 상태를 확인하는 절차를 더했습니다

바로 전날에는 파일을 잘못된 소스 세트에 두고도 빌드가 통과한 일이 있었습니다. 이번에는 명령을 실행했다는 사실만 보고 이미지도 올라갔다고 생각했습니다.

그래서 배포 절차의 마지막에 결과 확인을 넣었습니다. 종료 코드가 0인지 확인하는 것과 별도로, 스토어에서 읽은 이미지 해시를 로컬 파일과 비교합니다.
