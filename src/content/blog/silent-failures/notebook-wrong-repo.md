같은 날 배포 문서인 `releaser.md`에서 오류를 두 개 찾았습니다. 하나는 실행하면 바로 멈출 명령이었고, 다른 하나는 다른 제품을 덮어쓸 수 있는 주소였습니다.

낮에 확인한 절에는 `npm run lint && npm run build`가 적혀 있었습니다. 하지만 해당 저장소에 있는 스크립트는 `typecheck`, `test`, `build:web`였습니다.

밤에는 portfolio의 원격 저장소가 `twinkle-ai-labs.github.io`로 적혀 있는 것을 발견했습니다. 그 주소는 소개 홈인 web/home의 저장소였습니다. 포트폴리오의 원격은 `twinkle-ai-labs/portfolio`였습니다.

잘못된 명령은 3초 만에 발견할 수 있었습니다. 원격 주소 오류는 그날 홈을 두 번 배포하면서 저장소 이름을 확인한 덕분에 실행 전에 알아봤습니다. 실제로 홈을 덮어쓴 사건은 아닙니다.

## 없는 스크립트는 실행 단계에서 멈춥니다

문서에 적힌 `lint`를 실행하면 npm이 오류를 반환합니다.

```bash
$ npm run lint
npm error Missing script: "lint"
npm error
npm error To see a list of scripts, run:
npm error   npm run
```

명령이 없다는 사실을 1초 만에 알 수 있고, 사용 가능한 스크립트를 확인해 문서를 고칠 수 있습니다. 빌드나 배포를 진행하기 전에 실패하는 종류의 오류였습니다.

## 유효하지만 잘못된 원격은 배포를 막지 않습니다

포트폴리오를 빌드한 뒤 홈 저장소의 `gh-pages` 브랜치에 올리라는 지시는 문법상 틀리지 않았습니다. 그대로 실행했다면 다음 단계가 모두 성공할 수 있었습니다.

1. 포트폴리오를 빌드해 `dist/`를 만듭니다. 빌드가 성공하면 exit 0입니다.
2. 지정된 `twinkle-ai-labs.github.io`의 `gh-pages`에 푸시합니다. 권한이 있으면 이 단계도 exit 0입니다.
3. GitHub Pages가 받은 커밋으로 사이트를 배포합니다. 이 과정도 exit 0으로 끝날 수 있습니다.

그 경우 [twinklelabs.kr](https://twinklelabs.kr)에 회사와 제품을 소개하는 홈 대신 3D 포트폴리오가 표시됩니다. 각 단계의 성공 여부만으로는 잘못된 제품을 배포했다는 사실을 알 수 없습니다.

Git과 CI는 주어진 주소에 쓰기 권한이 있는지를 처리합니다. 인증 토큰(PAT)이 두 저장소에 모두 쓰기 권한을 가지고 있다면, 포트폴리오가 홈 저장소로 가고 있다는 제품 관계까지 판단하지는 않습니다.

## 문서의 주소도 배포 대상과 대조해야 합니다

소스 코드는 빌드와 타입 검사, 테스트를 거치지만 배포 문서의 저장소 주소는 그런 검사에 포함되지 않았습니다. 마크다운이 정상적으로 렌더링되고 주소 형식이 맞아도 대상 제품이 틀릴 수 있습니다. 문서의 명령을 실제로 쓰는 날에야 드러날 수 있는 문제였습니다.

이후에는 문서에서 주소를 복사하는 과정을 줄이는 방향으로 배포 절차를 정리했습니다.

- 원격 주소는 사람이 입력하지 않고 현재 프로젝트의 `package.json`이나 `git remote get-url origin`에서 읽도록 합니다.
- 현재 프로젝트 이름과 대상 Pages의 CNAME이 정해진 조합인지 확인하는 3줄짜리 가드를 배포 액션 앞에 둡니다.
- 문서의 명령을 각각 실행하는 대신 `npm run release` 한 진입점으로 묶어 검증한 경로를 사용하도록 합니다.

이번에는 저장소 이름을 기억하고 있어 잘못된 지시를 실행 전에 발견했습니다. 다음에도 같은 기억에 의존하지 않도록, 배포가 시작되기 전에 제품과 원격 주소의 조합을 확인하는 일이 필요했습니다.
