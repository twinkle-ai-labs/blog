Pocket PDF에 구독을 붙이면서 보상형 광고를 추가했습니다. 출시 빌드 직전, 이 광고 단위에 Google이 제공하는 테스트 ID가 남아 있는 것을 발견했습니다.

```
ca-app-pub-3940256099942544/...   ← 구글의 테스트용 견본
```

개발 중에는 광고가 표시됐고 로그와 보상 지급도 정상이었습니다. 테스트용 ID로는 기대한 동작이지만, 출시용 ID를 설정했다는 확인은 아니었습니다. 테스트 광고가 잘 뜨더라도 실제 광고를 내보낼 준비가 됐는지는 따로 확인해야 했습니다.

## 견본 검사는 통과하지 않았지만, 빈 값 검사는 빠져 있었습니다

테스트 ID를 잡은 것은 `admob-ids.sh`였습니다. 이 스크립트는 출시용 광고 ID가 견본인지, 비어 있는지를 각각 검사합니다.

견본 ID 검사에는 새 보상형 광고도 걸렸습니다. 그런데 빈 값 검사 목록에는 기존 배너와 전면 광고만 있었습니다. 보상형 ID를 비워두면 이 검사는 실패하지 않는 상태였습니다. 광고 유형을 추가하면서 검사 대상 목록을 갱신하지 않은 것입니다.

그래서 빈 값 검사에도 보상형을 추가했습니다. 스크립트가 성공했다는 사실뿐 아니라 새로 추가한 광고 유형도 검사하는지 확인해야 했습니다.

며칠 뒤 언어 파일에서도 비슷한 빈틈을 봤습니다. `strings-parity.sh`는 문자열 키의 개수가 맞아 통과했지만, 스페인어 파일에 영어 문장이 들어 있었습니다. 키를 비교하는 검사로는 값이 올바른 언어인지 알 수 없었습니다.

## 실제 ID를 발급받기 전까지는 빈 값으로 뒀습니다

발견 당시에는 AdMob 콘솔에서 실제 보상형 광고 단위를 발급받기 전이었습니다. 견본 ID를 남기는 대신 빈 값으로 바꿨습니다.

견본 ID가 나가면 테스트 광고가 사용자에게 표시됩니다. 빈 값이면 해당 광고를 불러오지 못합니다. 둘 다 출시 전에 해결해야 하지만 결과가 다르므로, 실제 ID가 준비되지 않은 상태를 빈 값으로 나타냈습니다.

보완한 검사는 빈 값도 실패로 처리합니다. 이제 실패 이유는 ‘견본 ID가 들어 있음’에서 ‘실제 ID가 아직 없음’으로 바뀌었습니다.

준비 상태도 광고 유형별로 분리했습니다. `isRewardedReady`를 배너의 `isReady`와 따로 두어, 보상형 ID가 없다는 이유로 이미 실제 ID를 가진 배너까지 멈추지 않도록 했습니다.

## 같은 커밋에서 프로모션 코드도 확인했습니다

PRO를 여는 프로모션 코드에는 sha256 해시 비교가 있었습니다. 그러나 그 앞에 개발 중 사용하던 평문 비교 넷이 `||`로 이어져 있었고, 그중 하나가 `"pro"`였습니다.

`pro`라는 단어만 입력해도 PRO가 열렸습니다. 해시 비교가 뒤에 있어도 앞의 조건이 참이면 검증을 통과하는 구조였습니다.

견본 광고 ID와 이 평문 조건은 모두 개발 중에는 기능이 잘 동작하는 것처럼 보였습니다. 출시를 준비하면서는 어떤 값과 조건으로 그 동작이 허용되는지 다시 확인해야 했습니다. 광고 검사에서는 특히 새 유형을 추가할 때 견본 검사와 빈 값 검사의 대상이 함께 늘어나는지 점검하게 됐습니다.
