두 앱 저장소의 `release.yml`에서 GitHub Actions 액션을 업데이트하다가 `gradle/actions/setup-gradle`은 요청받은 v6 대신 v5에 남겨두었습니다. 빌드 오류를 발견해서 멈춘 것은 아닙니다. 캐시의 기본 구현과 이용 조건이 바뀌어 따로 판단해야 했습니다.

## 새 캐시 입력의 기본값을 확인했습니다

v6의 `action.yml`에는 `cache-provider`가 추가돼 있었습니다.

```yaml
inputs:
  cache-provider:
    description: 'The cache provider to use'
    default: 'enhanced' # commercial caching service
```

기본값은 `enhanced`였고 상용 캐시 서비스를 사용한다고 적혀 있었습니다. 구현을 따라가 보니 캐시 기능이 `gradle-actions-caching`이라는 비공개 상용 구성요소로 분리돼 있었습니다.

캐시를 사용하는 두 앱의 워크플로에서는 버전 번호만 바꿔도 새 기본값을 검토해야 했습니다. 입력 형식이 호환되는지만 볼 일이 아니었습니다.

## LICENSE와 릴리스 노트도 달라졌습니다

v5의 LICENSE는 ‘The MIT License’ 단독이었습니다. v6에는 독점 구성요소(Proprietary components)가 포함된다는 안내가 추가돼 있었습니다.

릴리스 노트에는 v6으로 액션을 실행하면 Gradle의 상용 서비스 이용약관에 동의하는 것으로 간주한다는 설명도 있었습니다. 액션이 정상 실행되는지와 별개로, 그 조건을 받아들일지 정해야 했습니다.

메이저 버전을 올릴 때 API 변경이나 빌드 실패 가능성을 먼저 보곤 했습니다. 이번에는 그런 확인으로 이용 조건의 변경까지 판단할 수 없었습니다. Dependabot 등의 PR에서 CI가 통과하더라도 이 결정이 대신 이뤄지는 것은 아닙니다.

## 속도 개선을 확인한 뒤 내린 결정은 아닙니다

v6을 적용해 빌드 시간을 비교한 것은 아닙니다. 캐시가 빨라질 가능성과 새 이용 조건을 함께 검토하는 단계에서 멈췄습니다. 성능을 얼마나 개선할 수 있는지와 어떤 이용 조건을 받아들이는지는 별도로 판단해야 했습니다.

결국 `setup-gradle`은 v5.x의 안정 버전에 고정했습니다. 이번 워크플로에서는 새 구성요소를 도입하는 대신 기존 실행 환경을 유지하는 쪽을 선택했습니다.

앞으로 메이저 버전을 검토할 때는 코드와 입력뿐 아니라 LICENSE의 변경, 새 입력의 기본값, 외부 서비스 이용 조건도 함께 확인하기로 했습니다. 이번에 v5에 남은 이유는 기록해두고, 다시 올려야 할 시점에 같은 항목을 검토할 수 있도록 했습니다.
