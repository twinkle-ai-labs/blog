홈, 디자인 시스템, 약관 보관소, 블로그에 SEO를 적용하면서 빌드 성공만으로 확인할 수 없는 오류를 세 가지 찾았습니다. 정본 주소는 없는 페이지를 가리켰고, 한자 판별 정규식은 한글까지 걸러냈으며, 공유 카드가 한 장도 생성되지 않아도 빌드는 성공했습니다.

페이지를 열어 읽는 데는 문제가 없었습니다. 오류는 `<head>`의 주소와 별도로 생성하는 이미지 파일에 있었습니다.

## .html 주소를 레이아웃에 직접 전달했습니다

이 블로그는 Pelican을 사용하던 때의 주소를 유지합니다. 글과 일부 목록 페이지의 주소는 `.html`로 끝납니다.

```
/android/aapt-string-newline.html
/archives.html
```

정본 주소(canonical)를 만들 때는 현재 페이지의 pathname을 사용했습니다.

```ts
const canonical = new URL(Astro.url.pathname, SITE.url).href;
```

하지만 `Astro.url.pathname`에서 받은 값은 실제 파일 주소와 달랐습니다.

```
실제 주소   /android/aapt-string-newline.html
pathname   /android/aapt-string-newline/
```

GitHub Pages에는 뒤쪽 주소가 없어 404가 반환됐습니다. 글은 `.html` 주소에서 열리는데 검색 엔진에 안내하는 정본은 존재하지 않는 주소였습니다.

레이아웃이 pathname으로 주소를 추정하지 않도록 바꿨습니다. 실제 주소를 아는 페이지가 `path`를 전달합니다.

```astro
<Base path={postUrl(post)}>      <!-- /android/foo.html -->
<Base path="/archives.html">
```

글은 `postUrl(post)`를 쓰고 아카이브는 `/archives.html`을 명시합니다. 화면이 열린다는 확인과 정본 주소가 올바르다는 확인을 구분했습니다.

## 한자 범위에 한글이 포함돼 있었습니다

공유 카드인 OG 이미지는 코드로 생성하기로 했습니다. 사용하던 Pretendard에는 라틴, 한글, 가나가 있지만 한자는 없었습니다. 없는 글자를 그려 사각형(□)이 나오는 것을 피하려고, 한자가 포함된 제목은 카드 생성 대상에서 제외했습니다.

처음 작성한 정규식입니다.

```ts
// 이렇게 적었습니다
const HAN = /[㐀-䶿一-鿿豈-﫿]/;
```

마지막 범위의 시작 문자인 `豈`를 호환 한자 블록의 첫 글자 U+F900으로 잘못 알고 있었습니다. 실제 코드포인트는 U+8C48이었습니다.

```
의도한 것   U+F900 – U+FAFF   (호환 한자)
실제로 적힌 것  U+8C48 – U+FAFF   ← 한글(U+AC00~U+D7A3)이 이 안에 있어요
```

그 결과 한글 음절 범위인 U+AC00~U+D7A3이 검사 범위 안에 들어갔습니다.

```js
HAN.test('안드로이드를 만들며 배운 것')  // → true
```

한글 제목도 한자로 판정되면서 모든 글이 생성 대상에서 빠졌습니다. 카드가 한 장도 만들어지지 않은 이유였습니다.

범위를 눈에 보이는 글자 대신 코드포인트로 적어 수정했습니다.

```ts
// 글자가 아니라 번호로. 눈으로 맞히려 드는 순간 같은 실수가 또 납니다.
const HAN = /[\u3400-\u4DBF\u4E00-\u9FFF\uF900-\uFAFF]/;
```

이제 의도한 세 한자 블록의 시작과 끝을 코드에서 직접 확인할 수 있습니다.

## 생성할 카드가 0개여도 빌드는 성공했습니다

정규식이 잘못된 상태에서 빌드 로그는 다음과 같았습니다.

```
✓ Completed in 267ms.
[build] 68 page(s) built
```

HTML 68장을 만들었다는 기록은 있었지만, 글별 공유 카드가 0장이라는 표시는 없었습니다. 생성 대상이 모두 제외되면 이미지 생성 자체가 실패하지는 않았습니다.

결과물 폴더를 살펴보다가 `dist/og/`에 파일이 하나뿐인 것을 보고 문제를 알아챘습니다. 이후에는 생성한 HTML을 읽어, 각 문서가 가리키는 정본 주소와 OG 이미지 파일이 실제로 존재하는지 검사했습니다.

```
── blog ─ HTML 68장 (색인 65) · robots O · sitemap 65 URL
   ✗ /android/…: canonical 이 없는 주소
   ✗ /android/…: og:image 가 없는 파일
```

이 검사로 잘못된 canonical과 누락된 이미지 파일을 함께 찾을 수 있었습니다. 페이지 수가 맞거나 빌드가 끝났다는 확인만으로는 부족했던 부분입니다.

## Next.js 메타데이터에서는 중첩 객체가 교체됐습니다

같은 작업에서 Next.js의 `openGraph` 설정도 확인했습니다. 레이아웃에 이미지와 사이트 이름을 정하고 페이지에서 제목만 설정했습니다.

```ts
// layout.tsx — 이미지·사이트 이름을 정함
export const metadata = { openGraph: { images: [...], siteName: ... } }

// page.tsx — 제목만 적었는데
export const metadata = { openGraph: { title: '...' } }
```

이 설정에서는 페이지의 `openGraph`가 레이아웃의 객체를 필드별로 합치지 않고 교체했습니다. 제목만 바꾸려던 코드에서 이미지 설정까지 사라졌습니다. 빌드 오류는 없었지만 최종 메타데이터에는 기대한 이미지가 없었습니다.

## satori의 자간 설정을 제거했습니다

카드의 작은 머리말에 `letterSpacing: 2`를 적용했더니 한글 문장의 공백 하나가 사라졌습니다.

```
넣은 글자   안드로이드를 만들며 배운 것
그려진 글자  안드로이드를만들며 배운 것
```

다른 글자는 그대로였지만 두 낱말이 붙어 보였습니다. 해당 자간 설정을 제거해 원래 문장대로 표시되도록 했습니다.

## 정적 OG 이미지에 .png 주소를 부여했습니다

Next.js의 `opengraph-image` 규약으로 정적 내보내기를 했을 때는 확장자가 없는 파일이 만들어졌습니다.

```
out/opengraph-image      ← .png 가 아니에요
```

GitHub Pages에서 이 파일을 이미지로 제공하지 못하면 트위터나 슬랙처럼 공유 카드를 읽는 쪽에서도 그림으로 처리하지 못합니다. 확장자가 있는 주소를 직접 만들도록 바꿨습니다.

```
src/app/og.png/route.tsx  →  out/og.png   ← 진짜 PNG
```

이렇게 생성된 `out/og.png`를 메타데이터에서 가리키게 했습니다. 화면을 확인하는 것과 별개로, 최종 HTML의 주소가 실제 파일에 연결되는지까지 검사하는 절차가 필요했습니다.
