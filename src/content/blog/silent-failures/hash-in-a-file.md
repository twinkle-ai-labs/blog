커밋 작성자에 옛 이메일 주소가 남아 있어 `filter-branch`로 이력을 다시 썼습니다. 물타기 계산기 122개와 루트 32개, 모두 154개의 커밋이 대상이었습니다.

며칠 뒤 스토어 스크린샷 검사인 `fresh.sh`가 다음 오류로 실패하는 것을 발견했습니다.

```
fatal: bad object 8c7235f…
```

검사가 읽는 파일에는 이력을 다시 쓰기 전의 해시가 남아 있었습니다.

## reviewed-at이 가리키던 커밋을 찾을 수 없었습니다

이 검사는 스토어 스크린샷이 현재 앱 화면과 맞는지 확인하기 위한 것이었습니다. 사람이 화면을 검토한 시점의 커밋 해시를 `reviewed-at` 파일에 적어두고, 그 시점 이후 화면 코드가 바뀌었는지 확인합니다. 저장한 해시를 읽을 때는 `git log -1 <해시>`를 사용했습니다.

이력을 다시 쓰면서 커밋 해시는 바뀌었지만 `reviewed-at`은 갱신하지 않았습니다. 검사는 비교 기준을 읽는 단계에서 멈췄습니다.

```
fatal: bad object …
```

`bad object`는 스크린샷과 코드가 다르다는 뜻이 아닙니다. 비교에 필요한 커밋을 찾지 못했다는 뜻입니다. 검사 실패가 스크린샷의 최신 여부를 알려주는 신호로 이어지지 않은 이유였습니다.

## 백로그에 적어둔 주의사항을 놓쳤습니다

이 문제를 예상하지 못했던 것은 아닙니다. 백로그에는 다음 문장이 있었습니다.

> 이력을 다시 쓰면 `reviewed-at`도 어긋난다

그날 새벽에는 잘못 섞인 커밋을 되감을 때 이 파일이 깨질 수 있다는 이유로 되감기를 하지 않았습니다. 그런데 뒤이어 계획한 이력 재작성에서는 같은 파일을 놓쳤습니다.

주의사항은 남아 있었지만, 재작성 절차에 `reviewed-at`을 확인하는 단계가 없었습니다. 검사를 실행하는 도구도 이 파일을 새 해시로 바꿔주지는 않았습니다.

## 두 번째 재작성에서 참조도 함께 옮겼습니다

다시 작업할 때는 `filter-branch`의 `map`으로 옛 해시를 새 해시에 연결했습니다. 옮긴 곳은 두 종류였습니다.

- `reviewed-at` 파일에 저장한 해시
- 그 해시를 본문에 적어둔 커밋 메시지 둘

파일만 찾다가 커밋 메시지 안의 참조를 빠뜨릴 뻔했습니다. 검사 기준이 어디에 저장돼 있는지부터 확인해야 했습니다.

기록 금고의 일지에 적힌 옛 해시는 그대로 뒀습니다. 검사가 현재 이력에서 찾아야 하는 참조와, 당시의 작업을 기록한 해시는 용도가 달랐습니다.

| 위치 | 이력 재작성 뒤 처리 | 이유 |
|---|---|---|
| `reviewed-at` 같은 검사 입력 | 새 해시로 갱신 | 도구가 현재 저장소에서 커밋을 찾아야 합니다. |
| 일지·기록 | 당시 해시 유지 | 그때 어떤 정보를 기록했는지 남깁니다. |

## 다음 재작성 절차에 넣을 확인

먼저 해시를 담은 파일을 찾습니다.

```bash
git grep -E '[0-9a-f]{7,40}'
```

찾은 참조 중 도구가 사용하는 것은 `filter-branch`의 `map`이나 `git replace`를 이용해 함께 처리하려고 합니다.

검사가 해시를 읽을 때는 그 커밋이 실제로 있는지 먼저 확인합니다.

```bash
git cat-file -e "$REVIEWED_AT^{commit}" 2>/dev/null || {
  echo "reviewed-at 의 해시가 이 이력에 없다 — 이력이 다시 쓰였나?" >&2
  exit 1
}
```

이렇게 하면 비교 기준을 잃은 경우와 스크린샷이 낡은 경우를 구분해 알릴 수 있습니다. 이 확인은 백로그에만 남기지 않고 이력 재작성 절차에 넣기로 했습니다.

해시를 비교 기준으로 저장한 파일은 이력을 바꿀 때 함께 점검해야 합니다. 이번에 옮길 대상은 `reviewed-at`과 커밋 메시지였고, 일지의 과거 기록은 그대로 남겼습니다.
